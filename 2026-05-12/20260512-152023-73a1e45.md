+    private static String extractCommitSha(String diffContent) {
+        // 新commit: abc123def456... - message
+        for (String line : diffContent.split("\n")) {
+            if (line.startsWith("新commit:")) {
+                String fullSha = line.substring(line.indexOf(":") + 1).trim();
+                int spaceIdx = fullSha.indexOf(" ");
+                if (spaceIdx > 0) {
+                    fullSha = fullSha.substring(0, spaceIdx);
+                }
+                return fullSha.length() > 7 ? fullSha.substring(0, 7) : fullSha;
+            }
+        }
+        return "unknown";
+    }

——— 逐文件评审 ———

1. .github/workflows/main-maven-jar.yml  
  • 🟢优化  新增 4 个 secret 变量，写法正确，未在日志中回显，符合安全实践。  
  • 🟡建议  建议在 README 或仓库 secrets 设置说明中，标注这 4 个新 secret 为必填，避免 CI 失败。  

2. OpenAiCodeReview.java  
  • 🔴严重  reviewSummary 取值方式 reviewResult.split("\n")[0]，若 reviewResult 为空字符串会抛 ArrayIndexOutOfBoundsException；建议在 split 前先判断非空或改用 Optional.ofNullable(reviewResult).orElse("").  
  • 🟡建议  pushWechatNotification 只判断 null 未判断空字符串，getenv 可能返回 ""，应同时判断 isEmpty。  
  • 🟡建议  extractCommitSha / extractCommitMessage 出现格式不符时返回 "unknown"，不过后续微信模板字段长度受限，建议限制 CommitMsg 长度（微信 thing/character_string 最多 20/32 字符），超长需截断或省略。  
  • 🟢优化  在 catch 块仅打印栈而直接 System.exit(1)，保持了原有行为；新增微信异常只打印错误不退出，符合“不影响主流程”的设计。  
  • 🟡建议  推送使用原始 diffContent，而 AI 入参可能是截断版 truncatedDiff，两者不一致时 commit 信息仍可提取但若未来提取其它字段可能出错，可考虑直接复用 truncatedDiff。  

3. ReviewConfig.java  
  • 🟡建议  新增 env 读取方法简单直接，但每次调用都会触发 System.getenv，虽然开销小但可考虑缓存。  
  • 🟡建议  getRepoName 对空串处理正确，但未对大小写规范化；如需展示仓库链接建议 URLEncoder.encode(repoName, UTF-8)。  
  • 🟢肯定  将微信相关配置与 OpenAI 配置分离，保持类职责清晰，易于扩展。  

4. WeChatService.java  
  • 🔴严重  缓存 access_token 仅以静态单例保存，未按 appId 做维度，若同一进程推送多个公众号将串用 token；建议使用 Map<appId, TokenCache>。  
  • 🔴严重  readString(InputStream) 方法（虽未显示完整，但从用法看）如果内部未显式关闭输入流，会造成连接泄漏；应在 try-with-resources 中读取。  
  • 🟡建议  buildTemplateMessage 中各字段长度、字符集必须符合模板消息限制（thing≤20中文, character_string≤32等），目前直接塞入完整字符串，可能导致微信返回 40037/40036 错误。应在此处截断或做长度校验。  
  • 🟡建议  HttpURLConnection 的 inputStream / errorStream 未使用 try-with-resources，存在资源泄漏风险。  
  • 🟡建议  SEND_URL + accessToken 处未做 URL encoding，虽然 accessToken 通常为 URL 安全字符，但最好使用 URIBuilder 或 URLEncoder 以防万一。  
  • 🟡建议  cachedToken 过期时间计算 (expires_in - 300) 没有判断 json.getIntValue("expires_in") 是否存在且 >300；若 API 返回异常格式可能导致负数。  
  • 🟢肯定  使用同步方法保证多线程下 token 缓存一致性，且获取失败不影响主流程，健壮性较好。  
  • 🟢优化  推送异常统一捕获并友好日志，不影响后续流程。  

5. 其他通用问题  
  • 🟡建议  整个 SDK 仍大量使用 System.out/err，生产环境建议统一使用 slf4j + Logback 方便级别控制。  
  • 🟡建议  依赖 fastjson2，如项目对安全要求较高，需关注 fastjson 反序列化安全公告；本场景仅使用序列化/解析字符串，相对安全。  
  • 🟢肯定  getAccessToken、消息发送请求均设置了合适的超时时间（10s），避免在 CI 死等。

功能基本可用，但建议先修复 reviewResult 为空导致的越界、access_token 缓存维度不足及资源关闭问题，同时做好微信字段长度校验，以保证代码在各种边界场景下稳定运行。
